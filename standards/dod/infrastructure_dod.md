## Code Quality & Review

**[ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.**
- **Verification:** GitHub PR shows 2+ approvals, at least 1 from engineer with "Senior" or "Tech Lead" role.
- **Exception:** No exceptions.

**[ ] [L2] [ENG-4.1-SEC] PR includes approval from designated Security Champion (infrastructure changes are security-critical by default).**
- **Verification:** GitHub PR shows approval from engineer assigned Security Champion role in team config.
- **Exception:** No exceptions. All infrastructure changes require Security Champion review.

**[ ] [L1] [ENG-4.2] All commits are signed with GPG or SSH key registered in GitHub.**
- **Verification:** GitHub commit history shows "Verified" badge on all commits in PR.
- **Exception:** No exceptions.

**[ ] [L1] [ENG-4.2-CONV] All commit messages follow Conventional Commits format: type(scope): description.**
- **Verification:** GitHub Actions workflow "commitlint" passes. All commits match pattern: `(feat|fix|chore|docs|infra)\(.*\): .*`
- **Exception:** No exceptions.

**[ ] [L2] [SEC-4.1-TFPLAN] terraform plan output attached to PR showing no unintended resource deletions.**
- **Verification:** PR comment or artifact contains terraform plan output. Reviewer confirms no unintended "destroy" operations.
- **Exception:** No exceptions. Plan must be reviewed even for additions-only changes.

**[ ] [L2] [SEC-4.1-TFPLAN] Platform Engineering team approval documented in PR.**
- **Verification:** GitHub PR shows approval from at least 1 engineer in "Platform Engineering" team.
- **Exception:** No exceptions.

**[ ] [L2] [ENG-6.2-ADR] Architecture Decision Record (ADR) created in docs/adr/ for structural infrastructure changes (new service, data store, or cross-service contract).**
- **Verification:** `git diff` shows new file `docs/adr/NNNN-*.md`. ADR follows template (Context, Decision, Consequences).
- **Exception:** Not required for configuration-only changes (no new resources or architectural patterns).

**[ ] [L2] [ENG-6.2-ADR] Architecture Guild review approval documented in PR (if ADR created).**
- **Verification:** GitHub PR shows approval from at least 1 engineer in "Architecture Guild" team, or PR labeled "arch-review-complete".
- **Exception:** Only required if previous ADR criterion applies.

## Security & Compliance

**[ ] [L1] [SEC-3.1-SNYK] Snyk scan reports 0 Critical or High severity findings.**
- **Verification:** GitHub Actions workflow "snyk-security" passes. Snyk dashboard shows 0 Critical/High issues for branch.
- **Exception:** No exceptions. Critical/High findings must be fixed or have CISO-accepted risk waiver attached to PR.

**[ ] [L1] [SEC-3.1-SNYK] All Medium severity findings have tracked Jira tickets created and referenced in PR description.**
- **Verification:** PR description contains Jira ticket links (format: SEC-NNNN) for each Medium finding. Snyk comment on PR shows acknowledged findings.
- **Exception:** No exceptions.

**[ ] [L1] [SEC-3.2-SECRETS] Gitleaks scan passes with 0 secrets detected in CI.**
- **Verification:** GitHub Actions workflow "gitleaks" passes. No secrets detected in commit history.
- **Exception:** No exceptions.

**[ ] [L2] [SEC-4.1-TFPLAN] tfsec scan passes with 0 HIGH or CRITICAL findings.**
- **Verification:** GitHub Actions workflow "tfsec" passes. tfsec report shows 0 HIGH/CRITICAL issues.
- **Exception:** No exceptions. Findings must be fixed or suppressed with written justification in code comment.

**[ ] [L2] [SEC-4.2-SECRETS-MGMT] All new secrets documented as stored in AWS Secrets Manager or GitHub Actions secrets (not in code).**
- **Verification:** PR description or code comment documents secret name and storage location (AWS Secrets Manager ARN or GitHub Actions secret name).
- **Exception:** No exceptions. Secrets in code fail Gitleaks scan.

**[ ] [L3] [TEAM-KAFKA] Kafka topic ACLs configured for new topics (producer/consumer permissions documented in terraform).**
- **Verification:** Terraform config includes `kafka_acl` resources. PR description documents intended producer/consumer services.
- **Exception:** Only required if change creates new Kafka topics.

## Testing & Validation

**[ ] [L2] [QA-2.2-INT] Integration tests present and passing for infrastructure changes affecting service-to-service interactions (TestContainers or staging deployment verification).**
- **Verification:** JUnit 5 tests in `src/test/java` using TestContainers pass in CI, OR staging deployment smoke tests pass and evidence attached to PR.
- **Exception:** Not required for isolated infrastructure changes (e.g., monitoring config only).

**[ ] [L3] [TEAM-POSTGRES] Database migration tested with rollback verification (up/down scripts both execute cleanly in staging).**
- **Verification:** Staging deployment log shows migration applied successfully. Rollback tested and documented in PR comment.
- **Exception:** Only required if change includes PostgreSQL schema migrations.

**[ ] [L3] [TEAM-DR] Disaster recovery impact assessed and documented (RTO/RPO unchanged or new backup/restore procedure documented).**
- **Verification:** PR description includes DR impact statement. If RTO/RPO affected, `docs/runbooks/disaster-recovery.md` updated.
- **Exception:** Not required for ephemeral resources (e.g., CI/CD pipeline config).

## Documentation

**[ ] [L1] [L1-UNIVERSAL-DOC] Documentation updated (README, runbooks, architecture diagrams) where infrastructure change impacts operational procedures.**
- **Verification:** `git diff` shows updates to `docs/` directory. Reviewer confirms documentation matches infrastructure change.
- **Exception:** No exceptions. If no docs exist, create them. If no operational impact, add comment in PR: "No operational procedure changes."

**[ ] [L2] [QA-3.1-RELEASE] Runbook updated in docs/runbooks/ if operational procedures have changed (deployment steps, rollback, monitoring).**
- **Verification:** `git diff` shows updates to `docs/runbooks/*.md`. Updated sections clearly describe new operational procedures.
- **Exception:** Not required if infrastructure change has zero operational impact (e.g., internal refactoring).

**[ ] [L3] [TEAM-TERRAFORM] Terraform module README.md updated with input/output variable documentation (terraform-docs generated).**
- **Verification:** `terraform-docs markdown` generated and committed. README.md includes updated variable descriptions.
- **Exception:** Only required if change adds/modifies Terraform module variables.

## CI / Deployment Gate

**[ ] [L1] [L1-UNIVERSAL-CI] All GitHub Actions CI checks pass: terraform validate, terraform fmt, tfsec, Gitleaks, Snyk.**
- **Verification:** GitHub PR status shows all required checks green. No failing workflows.
- **Exception:** No exceptions.

**[ ] [L3] [TEAM-STAGING] Infrastructure change deployed to staging environment and validated (terraform apply executed, service health checks pass).**
- **Verification:** GitHub Actions workflow "deploy-staging" succeeded. Staging environment health dashboard shows green status.
- **Exception:** No exceptions. All infrastructure changes must be validated in staging before production.

## Acceptance & Sign-off

**[ ] [L2] [QA-3.1-RELEASE] Rollback plan documented and tested in staging environment.**
- **Verification:** PR description or linked document describes rollback procedure. Staging rollback test evidence attached (e.g., `terraform destroy` and re-apply log).
- **Exception:** No exceptions. Even additions-only changes require rollback plan (may be "terraform destroy resource X").

**[ ] [L3] [TEAM-EM-SIGNOFF] Engineering Manager sign-off documented in PR for production-impacting infrastructure changes (new services, data stores, or cross-AZ/region changes).**
- **Verification:** GitHub PR shows approval from Engineering Manager, or PR labeled "em-approved".
- **Exception:** Not required for non-production-impacting changes (e.g., dev environment only).
