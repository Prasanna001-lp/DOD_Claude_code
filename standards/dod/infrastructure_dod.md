## Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
**Verification:** GitHub PR page shows ≥2 approvals, with at least 1 from engineer with "Senior" or "Lead" title.  
**Exception:** No exceptions.

### [ ] [L2] [ENG-4.1-SEC] PR touching security-critical infrastructure has approval from designated Security Champion.
**Verification:** GitHub PR shows approval from engineer tagged as Security Champion in team roster.  
**Exception:** Not required if changes are non-security-critical (e.g., documentation-only). Tech Lead documents exemption in PR comment.

### [ ] [L1] [ENG-4.2] All commits are signed with GPG or SSH signing key registered in GitHub.
**Verification:** GitHub commit list shows "Verified" badge on all commits in PR.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-CONV] All commit messages follow Conventional Commits format: type(scope): description.
**Verification:** GitHub Actions workflow "Commit Lint" passes. Manual review confirms format compliance.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-MERGE] PR merged using squash merge strategy only; merge commits prohibited on main branch.
**Verification:** GitHub branch protection rules enforce squash merge. Merge button shows "Squash and merge" only.  
**Exception:** No exceptions.

### [ ] [L2] [ENG-6.2] ADR document created in docs/adr/ for architecture, data model, or cross-service contract changes.
**Verification:** Git diff shows new or modified file matching docs/adr/NNNN-*.md pattern.  
**Exception:** Not required if change is purely operational (e.g., parameter tuning) with no architectural impact. Tech Lead documents exemption in PR description.

### [ ] [L2] [ENG-6.2] Architecture Guild review approval documented in PR (comment or approval from guild member).
**Verification:** GitHub PR shows approval or explicit "Approved for architectural changes" comment from member of Architecture Guild roster.  
**Exception:** Not required if no ADR was needed (operational change only). Exemption documented by Tech Lead.

### [ ] [L3] [TEAM-INFRA-01] Terraform fmt passes with zero formatting violations.
**Verification:** CI workflow "Terraform Format Check" passes. Run: `terraform fmt -check -recursive`  
**Exception:** No exceptions.

## Security

### [ ] [L1] [SEC-3.1] Snyk scan shows 0 Critical or High severity findings in CI before merge to main.
**Verification:** GitHub Actions workflow "Snyk Security Scan" passes with exit code 0. Snyk dashboard shows no Critical/High findings for this PR.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.1] All Medium severity findings from Snyk acknowledged with tracked Jira ticket referenced in PR.
**Verification:** PR description contains Jira ticket links (format: JIRA-NNNN) for each Medium finding listed in Snyk report.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.2] Gitleaks scan passes in CI with zero secrets detected before merge to main.
**Verification:** GitHub Actions workflow "Gitleaks Secret Scan" passes with exit code 0. No findings in Gitleaks report.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.3-APPROVED] All third-party dependencies are listed in approved dependency registry (verified in CI).
**Verification:** GitHub Actions workflow "Dependency Check" passes. All dependencies in Terraform modules match entries in approved-dependencies.yaml.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.3-CVE] No dependencies with Critical CVEs older than 5 business days present.
**Verification:** CI dependency scanner (Snyk or equivalent) reports 0 Critical CVEs with disclosure date >5 business days ago.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-4.2] All secrets stored in AWS Secrets Manager or GitHub Actions secrets (verified via code review).
**Verification:** Code review confirms: no hardcoded credentials in .tf files. All sensitive values reference AWS Secrets Manager ARNs or GitHub Actions secret variables.  
**Exception:** No exceptions.

### [ ] [L2] [SEC-4.1-PLAN] terraform plan executed and produces clean plan with no unintended resource deletions (plan output attached to PR).
**Verification:** PR contains comment or artifact with full terraform plan output. Manual review confirms: (1) no resources marked for destruction unless explicitly intended, (2) no unexpected changes to existing resources.  
**Exception:** No exceptions.

### [ ] [L2] [SEC-4.1-PLAN] Platform Engineering team review approval documented in PR.
**Verification:** GitHub PR shows approval from engineer tagged as "Platform Engineering" in team roster.  
**Exception:** No exceptions.

## Documentation

### [ ] [L2] [INFRA-DOC-01] Runbook updated if operational procedures changed (docs/runbooks/ or wiki entry modified).
**Verification:** Git diff shows modification to files under docs/runbooks/ OR Confluence page "Infrastructure Runbooks" shows recent edit timestamp matching PR date.  
**Exception:** Not required if change is purely additive (e.g., new resource with no operational impact). Tech Lead documents exemption in PR description.

### [ ] [L3] [TEAM-INFRA-03] Terraform module README.md updated with usage examples and variable descriptions for any new or modified modules.
**Verification:** Git diff shows README.md in modified Terraform module directories. README contains: (1) module purpose, (2) usage example, (3) table of input variables, (4) table of outputs.  
**Exception:** Not required for minor variable changes (e.g., default value updates). Tech Lead approves exemption in PR comment.

### [ ] [L2] [INFRA-DOC-02] Disaster Recovery verification documented if change impacts backup/restore procedures.
**Verification:** PR description or linked Confluence page confirms: DR procedure tested in staging, or explicit statement that DR procedures are unaffected.  
**Exception:** Not required if change does not involve stateful resources (databases, storage, Kafka). Platform Engineering Lead approves exemption.

2. **Automated rollback testing in staging** — Currently: documented rollback procedure, manual verification. Target: CI workflow that applies infrastructure, then rolls back and verifies state consistency.

3. **Terraform state encryption verification** — Currently: assumed via backend configuration. Target: CI check explicitly verifies state file encryption at rest.

4. **Multi-region disaster recovery simulation** — Currently: annual manual DR exercise. Target: automated DR simulation per infrastructure PR affecting critical stateful resources.
