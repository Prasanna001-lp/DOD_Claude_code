## Code Quality & Review

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
**Verification:** GitHub PR page shows 2+ approvals with at least 1 senior engineer approval before merge.  
**Exception:** No exceptions.

### [ ] [L3] [ENG-4.1-SEC] PR touching security-critical code has 3rd approval from Security Champion.
**Verification:** GitHub PR shows approval from designated Security Champion if PR modifies IAM policies, security groups, KMS keys, or secrets management.  
**Exception:** EM can grant exemption with written justification if Security Champion unavailable (must be resolved within 24 hours).

### [ ] [L1] [ENG-4.2-SIGN] All commits in PR are signed with GPG or SSH key verified by GitHub.
**Verification:** GitHub PR commits page displays "Verified" badge on all commits.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-MSG] All commit messages follow Conventional Commits format verified by CI lint.
**Verification:** GitHub Actions workflow "Commit Lint" check passes with green status.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-MERGE] PR merged to main using squash merge strategy (GitHub branch protection enforced).
**Verification:** GitHub branch protection rule enforces squash merge. Verify in branch settings: Settings → Branches → main → "Require linear history" enabled.  
**Exception:** No exceptions.

## Infrastructure-as-Code

### [ ] [L2] [SEC-4.1-TERRAFORM] terraform plan output attached to PR showing no unintended resource deletions.
**Verification:** PR description or comment contains terraform plan output. Review plan for unexpected "destroy" or "replace" operations on production resources.  
**Exception:** No exceptions. Intentional deletions must be explicitly documented and approved by EM.

### [ ] [L2] [SEC-4.1-TERRAFORM] Platform Engineering team approval documented in PR.
**Verification:** GitHub PR shows approval from @platform-engineering team member or designated Platform Engineering reviewer.  
**Exception:** No exceptions. Cannot merge infrastructure changes without Platform Engineering review.

### [ ] [L2] [SEC-4.1-TERRAFORM] tfsec scan passes with 0 HIGH or CRITICAL findings in CI.
**Verification:** GitHub Actions workflow "tfsec Security Scan" check passes. Review tfsec report in workflow logs confirms 0 HIGH/CRITICAL findings.  
**Exception:** No exceptions. HIGH/CRITICAL findings must be remediated before merge or have CISO-accepted risk waiver attached to PR.

### [ ] [L2] [ENG-6.2-ARCH] ADR created in docs/adr/ following ADR template if change affects architecture, data model, or service contracts.
**Verification:** If PR changes network topology, introduces new AWS services, modifies data storage patterns, or alters service dependencies: ADR file exists in docs/adr/ using numbered format (e.g., 0015-migrate-to-ecs-fargate.md).  
**Exception:** Not required for minor config changes (e.g., scaling parameters, log retention). Tech Lead approval required to skip ADR.

### [ ] [L2] [ENG-6.2-ARCH] Architecture Guild approval documented in PR (comment or approval from guild member).
**Verification:** If ADR required: GitHub PR shows comment or approval from Architecture Guild member (@architecture-guild) acknowledging ADR review.  
**Exception:** Not required if no ADR created. Tech Lead confirms ADR not applicable.

### [ ] [L3] [TEAM-INFRA-DR] Disaster recovery verification completed for stateful resources.
**Verification:** If PR modifies RDS, S3, DynamoDB, or other stateful services: runbook in docs/runbooks/ updated with backup/restore procedures. DR test documented in PR (restore from backup verified in staging).  
**Exception:** EM approval required to defer DR testing to post-merge if change is time-sensitive. Must be completed within 5 business days.

## Security

### [ ] [L1] [SEC-3.1-SNYK] Snyk scan shows 0 Critical or High severity findings in GitHub Actions CI.
**Verification:** GitHub Actions workflow "Snyk Security Scan" check passes. Review Snyk dashboard confirms 0 Critical/High vulnerabilities in infrastructure dependencies (Terraform providers, modules).  
**Exception:** No exceptions. Critical/High findings must be fixed or have CISO-accepted risk waiver before merge.

### [ ] [L1] [SEC-3.1-SNYK] All Medium severity Snyk findings have tracked Jira tickets linked in PR description.
**Verification:** PR description contains Jira ticket links for each Medium severity finding. Jira tickets assigned and scheduled for remediation.  
**Exception:** No exceptions. Medium findings acknowledged does not mean ignored — must be tracked.

### [ ] [L1] [SEC-3.2-SECRETS] Gitleaks scan passes in GitHub Actions CI with 0 secrets detected.
**Verification:** GitHub Actions workflow "Gitleaks Secrets Scan" check passes with exit code 0.  
**Exception:** No exceptions. If false positive: add to .gitleaksignore with justification comment and Security Champion approval.

### [ ] [L1] [SEC-3.3-DEPS] All new Terraform providers or modules listed in approved dependency registry before merge.
**Verification:** If PR introduces new Terraform providers or modules not in approved-dependencies.yaml: PR description includes link to dependency approval ticket. Approved-dependencies.yaml updated in same PR.  
**Exception:** No exceptions. Unapproved dependencies cannot be merged.

### [ ] [L1] [SEC-4.2-SECRETS-MGMT] All secrets stored in AWS Secrets Manager or GitHub Actions secrets, verified by Gitleaks scan.
**Verification:** Terraform code references secrets via data.aws_secretsmanager_secret or GitHub Actions secrets. Gitleaks scan passes (SEC-03). No hardcoded credentials in .tf files.  
**Exception:** No exceptions. Hardcoded secrets are a critical security violation.

## Documentation

### [ ] [L2] [TEAM-INFRA-RUNBOOK] Runbook created or updated in docs/runbooks/ for new or modified infrastructure.
**Verification:** If PR introduces new AWS services or changes deployment procedures: runbook file exists in docs/runbooks/ with sections: Purpose, Prerequisites, Deployment Steps, Rollback Steps, Monitoring, Troubleshooting.  
**Exception:** Not required for minor config-only changes. Tech Lead approval to skip.

### [ ] [L3] [TEAM-INFRA-DIAGRAM] Architecture diagram updated in docs/architecture/ if network topology or service dependencies change.
**Verification:** If PR modifies VPC structure, security groups, load balancers, or introduces new service integrations: diagram file (PNG or draw.io) updated showing current state.  
**Exception:** Not required if no architectural change. Tech Lead confirms diagram unchanged.

## CI / Deployment Gate

### [ ] [L1] [TEAM-CI-ALL-CHECKS] All GitHub Actions CI checks pass (lint, validate, security scan, plan).
**Verification:** GitHub PR checks page shows all required workflows green: terraform fmt, terraform validate, tflint, tfsec, Snyk, Gitleaks, terraform plan.  
**Exception:** No exceptions. All CI checks must pass before merge.

### [ ] [L2] [TEAM-INFRA-PLAN-REVIEW] Terraform plan reviewed and approved by Platform Engineering team.
**Verification:** Platform Engineering reviewer explicitly comments "Terraform plan approved" or equivalent on PR after reviewing plan output.  
**Exception:** No exceptions. Infrastructure changes cannot merge without plan approval.

## Acceptance & Sign-off

### [ ] [L2] [TEAM-INFRA-VERIFICATION] Infrastructure change verified in staging or pre-prod environment before production deploy.
**Verification:** PR description or comment documents successful terraform apply in staging. Verification steps completed: resources created, networking tested, monitoring alerts configured.  
**Exception:** Emergency hotfixes (P1 incidents): EM approval to deploy directly to production with post-deploy verification within 2 hours.

### [ ] [L3] [TEAM-INFRA-MONITORING] Monitoring and alerting configured for new infrastructure resources.
**Verification:** If PR creates new AWS resources (EC2, RDS, Lambda, etc.): CloudWatch alarms or Datadog monitors configured. Alert definitions documented in runbook or IaC.  
**Exception:** Not required for ephemeral resources (e.g., staging environment). Tech Lead approval to skip.

## Future Candidates (Not Yet Practised)

The following criteria represent aspirational quality gates not currently enforced by the team. They are documented here for future implementation consideration:

- **Terraform state locking verification** — S3 backend with DynamoDB lock table configured before applying changes to prevent concurrent modification conflicts.
- **Cost estimation using Infracost** — Automated cost analysis in CI before merging infrastructure changes exceeding $500/month impact.
- **Terraform module versioning enforcement** — All module sources pinned to specific version tags (not `latest` or branch references) to ensure reproducible deployments.
- **AWS Config compliance rules verification** — All resources validated against organizational compliance rules before deployment.
- **Service Control Policy (SCP) testing** — SCP changes tested in isolated AWS account before org-wide deployment to prevent lockout scenarios.
