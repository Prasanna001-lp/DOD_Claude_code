## Overview

This Definition of Done applies to **all bug fix work items** in the Commerce Platform team. Every criterion must be satisfied before a bug fix can be merged to `main` and deployed to production.

**Criterion Layers:**
- **[L1-UNIVERSAL]** — Applies to ALL work items, no exceptions, EM + CISO sign-off to modify
- **[L2-WORKTYPE]** — Applies to ALL bug fixes, EM can grant one-sprint exemption with written justification
- **[L3-TEAM]** — Commerce Platform team-specific, Tech Lead approval, reviewed quarterly
- **[L4-STORY]** — Story-specific, added during grooming by PO or Tech Lead

## 1. Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
**Verification:** GitHub branch protection rules enforce 2 approvals; PR approval list shows ≥1 senior engineer.  
**Exception:** No exceptions.

### [ ] [L2] [ENG-4.1-SEC] PRs touching security-critical paths (authentication, payment processing, PII handling) have 3rd approval from Security Champion (@security-champion).
**Verification:** GitHub PR shows approval comment from Security Champion user account.  
**Exception:** No exceptions for security-critical paths.

### [ ] [L1] [ENG-4.2-SIGN] All commits are signed with GPG or SSH signing key registered in GitHub.
**Verification:** GitHub shows "Verified" badge on all commits in PR.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-FORMAT] All commit messages follow Conventional Commits format: type(scope): description.
**Verification:** GitHub Actions commitlint check passes in CI workflow.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-MERGE] PR uses squash merge strategy; no merge commits on main branch.
**Verification:** GitHub merge strategy dropdown shows "Squash and merge" selected; main branch history shows no merge commits.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-COMPLEXITY] SonarQube quality gate passes: cyclomatic complexity ≤10 per method.
**Verification:** SonarQube CI check passes; complexity violations = 0 in SonarQube dashboard.  
**Exception:** No exceptions.

### [ ] [L2] [ENG-4.3-LOC] No method exceeds 50 lines of code.
**Verification:** SonarQube reports 0 violations for "Methods should not have too many lines"; code review confirms.  
**Exception:** Tech Lead approval with ADR required for rare complex algorithms.

### [ ] [L2] [ENG-4.3-DEAD] SonarQube reports zero dead code violations; no commented-out code blocks in diff.
**Verification:** SonarQube "Dead stores" and "Unused" rules report 0 issues; git diff shows no commented blocks.  
**Exception:** No exceptions.

## 2. Test Coverage & Quality

### [ ] [L1] [QA-2.1-COVERAGE-LINE] JaCoCo reports ≥80% line coverage on all changed modules in CI.
**Verification:** GitHub Actions JaCoCo report shows ≥80% line coverage for all changed Java packages.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COVERAGE-BRANCH] JaCoCo reports ≥75% branch coverage on all changed modules in CI.
**Verification:** GitHub Actions JaCoCo report shows ≥75% branch coverage for all changed Java packages.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-NO-REGRESSION] CI coverage check passes: no regression on existing covered code.
**Verification:** GitHub Actions JaCoCo check passes; coverage delta report shows 0% loss on existing modules.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-UNIT] Unit tests present and passing in CI (JUnit 5).
**Verification:** GitHub Actions test report shows new/modified unit tests passing in `src/test/java`; test class name matches bug ticket ID pattern.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-INTEGRATION] Integration test covering integration layer present if bug is integration-related (database, Kafka, external API).
**Verification:** GitHub Actions test report shows integration test passing in `src/integration-test/java` if bug involves integration layer.  
**Exception:** Bug fixes may skip if bug is purely unit-level (Tech Lead approval required with comment in PR).

### [ ] [L2] [QA-2.2-E2E-BUGFIX] E2E test covering UI bug reproduction path present if bug is UI-related (React component, user flow).
**Verification:** GitHub Actions Playwright report shows UI regression test passing in `e2e/specs/`; test references bug ticket ID.  
**Exception:** Non-UI bugs exempt.

### [ ] [L2] [QA-2.3-REGRESSION] [From INC-003] Regression test covering exact bug reproduction path from original report present in CI.
**Verification:** GitHub Actions test report shows regression test passing; test class/method name references original bug ticket ID; test demonstrates failure on pre-fix code and success on fixed code.  
**Exception:** No exceptions.  
**Note:** This criterion reinforces the mandate from escaped defect INC-003 where bug INC-001 reappeared due to missing regression test.

### [ ] [L3] [TEAM-COMMERCE] README.md or relevant service documentation updated if fix changes external behavior or API response format.
**Verification:** `git diff` shows `README.md` or `docs/` updated if bug fix affects documented behavior; otherwise N/A confirmed in PR description.  
**Exception:** No documentation update needed if fix is purely internal (PO confirms in PR comment).
