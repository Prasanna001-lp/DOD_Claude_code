## Purpose

This Definition of Done ensures that every bug fix merged to the Commerce Platform codebase:
- Resolves the root cause of the original defect
- Includes automated regression tests to prevent recurrence
- Meets all security, quality, and compliance standards
- Is verified by the original reporter or QA team

## How to Use This Checklist

1. **During Bug Triage**: Tech Lead and assignee review this DoD and add any [L4] story-specific criteria in the Jira ticket
2. **During Development**: Developer works through each criterion, checking them off in the PR description
3. **During Code Review**: Reviewers verify all criteria are met before approving
4. **Before Merge**: CI pipeline enforces all [L1] universal gates automatically

## Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead
**Verification:** GitHub PR shows 2+ approvals; at least one reviewer has "Senior Engineer" or "Tech Lead" role visible in GitHub profile or org chart.  
**Exception:** No exceptions.

### [ ] [L2] [ENG-4.1-SEC] If PR modifies authentication, authorization, payment processing, or PII handling, Security Champion approval is present
**Verification:** Security Champion tagged and approved PR (visible in PR reviewers list).  
**Exception:** Not applicable if bug fix does not touch security-critical paths.

### [ ] [L1] [ENG-4.2-SIGN] All commits in PR are signed with GPG or SSH key registered in GitHub
**Verification:** GitHub displays "Verified" badge on all commits in PR.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-CONV] All commit messages follow Conventional Commits format: type(scope): description
**Verification:** commitlint GitHub Actions check passes; all commits match pattern `fix(scope): description`.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-MERGE] PR is configured for squash merge; merge commits to main are blocked by branch protection
**Verification:** GitHub PR interface shows "Squash and merge" button; branch protection rules visible in repo settings.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-COMPLEXITY/LOC/DEAD] SonarQube quality gate passes: cyclomatic complexity ≤10 per method, no methods >50 lines of code, 0 dead code issues
**Verification:** SonarQube status check passes in GitHub; SonarQube dashboard shows Quality Gate = Passed.  
**Exception:** No exceptions.

### [ ] [L2] [BUG-FIX-ROOT-CAUSE] Root cause documented in PR description or linked Jira ticket, identifying why the bug occurred
**Verification:** PR description or Jira ticket contains "Root Cause:" section with analysis.  
**Exception:** No exceptions for P1/P2 bugs. P3/P4 bugs may have brief root cause in commit message.

## Test Coverage & Quality

### [ ] [L1] [QA-2.1-COVERAGE] JaCoCo reports ≥80% line coverage on changed modules in CI
**Verification:** JaCoCo CI check passes; coverage report shows changed files meet 80% threshold.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COVERAGE] JaCoCo reports ≥75% branch coverage on changed modules in CI
**Verification:** JaCoCo CI check passes; coverage report shows changed files meet 75% branch coverage threshold.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COVERAGE] CI build verifies no coverage regression: existing covered code maintains or improves coverage
**Verification:** JaCoCo diff report in CI logs shows no files with reduced coverage percentage.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-UNIT] Unit tests present for all new/changed methods using JUnit 5 and Mockito
**Verification:** Test files in `src/test/java/` cover changed methods; CI runs unit test suite and reports pass.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-INTEGRATION] Integration test covering the integration point that failed (if bug was integration-related)
**Verification:** Integration test file in `src/test/integration/` tests the specific service-to-service or service-to-database interaction; CI passes integration suite.  
**Exception:** Not applicable if bug was isolated to single service logic (unit-level bug).

### [ ] [L2] [QA-2.2-E2E] Playwright E2E test reproduces the UI bug scenario and verifies the fix (if bug was UI-related)
**Verification:** Playwright test file in `tests/e2e/` reproduces bug scenario; test passes on fixed code; CI E2E suite passes.  
**Exception:** Not applicable if bug was backend-only (API/service bug).

### [ ] [L2] [QA-2.3-REGRESSION / From INC-003] Regression test covers exact reproduction path from original bug report. Test fails on pre-fix commit and passes on fix commit
**Verification:** Test file references original bug ticket number in test name or comments; PR description or CI logs show test failed on pre-fix commit SHA and passed on fix commit SHA.  
**Exception:** No exceptions.  
**⚠️ Escaped Defect Criterion** — This criterion was added after incident INC-003 (P2 defect recurrence).

## Security

### [ ] [L1] [SEC-3.1-SNYK] Snyk scan reports 0 Critical or High severity findings
**Verification:** Snyk CI check passes in GitHub Actions workflow; Snyk dashboard shows 0 Critical/High issues.  
**Exception:** No exceptions. Findings must be fixed or have CISO-accepted risk waiver documented in Jira.

### [ ] [L1] [SEC-3.1-SNYK] All Medium severity findings from Snyk have corresponding Jira tickets linked in PR description
**Verification:** PR description contains Jira ticket links (e.g. SEC-123) for each Medium finding listed in Snyk report.  
**Exception:** No exceptions. Medium findings may remain unfixed but must be tracked.

### [ ] [L1] [SEC-3.2-SECRETS] Gitleaks scan passes in CI with 0 secrets detected
**Verification:** Gitleaks GitHub Actions check passes; no alerts in Security tab.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.3-DEPS] mvn dependency:check (for Java) or npm audit (for React) reports 0 Critical CVE findings in CI
**Verification:** Maven dependency-check or npm audit CI step passes; no Critical vulnerabilities in report.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-4.2-SECRETS-MGMT] All secrets stored in AWS Secrets Manager or GitHub Actions secrets. Verified by Gitleaks scan passing
**Verification:** Gitleaks passes (SEC-03); code review confirms no hardcoded credentials in changed files.  
**Exception:** No exceptions.

## Documentation

### [ ] [L2] [BUG-FIX-DOCS] Documentation updated if bug fix changes API behavior, configuration, or operational procedures
**Verification:** README.md, API docs, or Confluence runbook updated with changes; or PR description states "No doc changes required" with justification.  
**Exception:** Not applicable if bug fix is internal implementation change with no external impact.

### [ ] [L3] [COMMERCE-PLATFORM-JIRA] Original Jira bug ticket updated with resolution notes and linked to PR
**Verification:** Jira ticket shows status = Resolved; PR link in Jira comments; resolution notes describe fix approach.  
**Exception:** No exceptions.

## CI / Deployment Gate

### [ ] [L1] [CI-ALL-CHECKS] All GitHub Actions CI checks pass: build, lint, unit tests, integration tests, coverage, SonarQube, Snyk, Gitleaks, dependency check
**Verification:** GitHub PR shows all status checks green; no failing checks in Actions tab.  
**Exception:** No exceptions.

### [ ] [L2] [BUG-FIX-STAGING] Bug fix deployed and manually verified in staging environment before merging to main
**Verification:** PR comment or Jira ticket documents staging deployment and manual test result.  
**Exception:** May be skipped for low-risk P3/P4 bugs with comprehensive automated test coverage. Requires Tech Lead approval documented in PR.

## Acceptance & Sign-off

### [ ] [L2] [BUG-FIX-REPORTER] Bug reporter or QA verifies fix resolves original issue (for P1/P2 bugs)
**Verification:** Jira ticket comment from original reporter or QA confirming fix verified in staging; or PR comment with verification evidence.  
**Exception:** Not required for P3/P4 bugs if automated regression test provides sufficient coverage.

### [ ] [L3] [COMMERCE-PLATFORM-PO] Product Owner sign-off obtained (for P1 customer-impacting bugs)
**Verification:** PO approval comment on PR or Jira ticket; or PO tagged and acknowledged in PR.  
**Exception:** Not required for internal/technical bugs with no customer impact.

## Exemption Process

**Cannot be overridden.** To modify an L1 criterion, contact:
- Engineering Manager (@Prasanna001-lp)
