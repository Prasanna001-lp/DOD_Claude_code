## 📋 How to Use This Checklist

1. **Review during grooming** — Tech Lead and team walk through L1 + L2 + L3 criteria for every bug fix story.
2. **Add L4 if needed** — Product Owner or Tech Lead adds story-specific criteria in the L4 section during grooming.
3. **Verify before merge** — Every criterion must be satisfied before PR merge. No exceptions unless explicitly documented.
4. **Track exemptions** — If EM grants a one-sprint exemption for L2 criteria, document in Jira ticket and DoD Review log.

## 🔹 Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
**Verification:** GitHub PR approval count shows ≥ 2 approvals. At least 1 approval from an engineer with "Senior Engineer" or "Tech Lead" role in GitHub team settings.  
**Exception:** No exceptions.

---

### [ ] [L2] [ENG-4.1-SEC] PR touching security-critical paths has approval from Security Champion.
**Verification:** If PR modifies files in `auth/`, `security/`, or `crypto/` directories, GitHub PR shows approval from user with "Security Champion" role.  
**Exception:** Not applicable if PR does not touch security-critical paths.

---

### [ ] [L1] [ENG-4.2-SIGN] All commits are signed with GPG or SSH key registered in GitHub.
**Verification:** GitHub shows "Verified" badge on all commits in the PR. CI enforces commit signature verification.  
**Exception:** No exceptions.

---

### [ ] [L1] [ENG-4.2-CONV] All commit messages follow Conventional Commits format: type(scope): description.
**Verification:** GitHub Actions runs commitlint check. CI passes with zero commit message violations.  
**Exception:** No exceptions.

---

### [ ] [L1] [ENG-4.2-MERGE] PR merged using squash merge strategy (no merge commits on main).
**Verification:** GitHub PR settings enforce "Squash and merge" only. Main branch protection rule blocks merge commits.  
**Exception:** No exceptions.

---

### [ ] [L1] [ENG-4.3-COMPLEXITY] SonarQube quality gate passes: cyclomatic complexity ≤ 10 per method.
**Verification:** SonarQube CI check passes. Quality gate shows zero methods with complexity > 10.  
**Exception:** No exceptions.

---

### [ ] [L1] [ENG-4.3-LOC] No method exceeds 50 lines of code (SonarQube enforces).
**Verification:** SonarQube CI check passes. Quality gate shows zero methods with LOC > 50.  
**Exception:** No exceptions.

---

### [ ] [L1] [ENG-4.3-DEAD] SonarQube reports zero dead code issues (unreachable, commented-out code removed).
**Verification:** SonarQube CI check passes. Quality gate shows zero dead code issues.  
**Exception:** No exceptions.

## 🧪 Test Coverage & Quality

### [ ] [L1] [QA-2.1-LINE] JaCoCo reports ≥ 80% line coverage on all changed modules in CI.
**Verification:** JaCoCo CI check passes. Coverage report attached to PR shows ≥ 80% line coverage on changed modules.  
**Exception:** No exceptions.

---

### [ ] [L1] [QA-2.1-BRANCH] JaCoCo reports ≥ 75% branch coverage on changed modules in CI.
**Verification:** JaCoCo CI check passes. Coverage report shows ≥ 75% branch coverage on changed modules.  
**Exception:** No exceptions.

---

### [ ] [L1] [QA-2.1-REGRESS] CI coverage check passes: no existing covered code has lost coverage.
**Verification:** JaCoCo CI check compares coverage against main branch. Build fails if any previously covered line loses coverage.  
**Exception:** No exceptions.

---

### [ ] [L2] [QA-2.2-BUG-UNIT] Unit tests (JUnit 5) covering bug fix present and passing.
**Verification:** CI test run passes. Test report shows unit tests executed for bug fix code path.  
**Exception:** No exceptions.

---

### [ ] [L2] [QA-2.2-BUG-UNIT] Integration tests present and passing if bug was in service integration layer.
**Verification:** CI test run passes. Test report shows integration tests executed if bug involved service-to-service communication or database integration.  
**Exception:** Not applicable if bug was isolated to single module with no integration points.

---

### [ ] [L2] [QA-2.2-BUG-UNIT] E2E tests (Playwright) present and passing if bug was in UI layer.
**Verification:** CI test run passes. Test report shows Playwright E2E tests executed if bug affected user interface or user journey.  
**Exception:** Not applicable if bug was in backend service with no UI impact.

---

### [ ] [L2] [QA-2.3-REGRESSION / From INC-003] Regression test covering exact reproduction path from original bug report present in CI.
**Verification:** Test file references bug ticket number in test method name or comment. PR description includes evidence that test failed pre-fix and passes post-fix (screenshot or CI run link).  
**Exception:** No exceptions.  
**🔴 Escaped Defect Criterion** — derived from production incident INC-003.

---

### [ ] [L3] [TEAM-SPRING-BOOT] Spring Boot integration tests use @SpringBootTest with appropriate test slices (@DataJpaTest, @WebMvcTest) where applicable.
**Verification:** Integration test classes use Spring Boot test annotations. Tests execute against embedded database (H2) or test containers where appropriate.  
**Exception:** Tech Lead approval if alternative testing approach justified.

## 🔒 Security

### [ ] [L1] [SEC-3.1-SNYK / SEC-3.3-DEPS] Snyk scan shows 0 Critical or High severity findings. All Medium findings have tracked Jira tickets. No Critical CVEs older than 5 business days.
**Verification:** Snyk CI check passes in GitHub Actions workflow. Jira ticket references present in PR description for Medium findings. Snyk report shows zero Critical CVEs with age > 5 business days.  
**Exception:** No exceptions.

---

### [ ] [L1] [SEC-3.2-SECRETS / SEC-4.2-SECRETS-MGMT] Gitleaks scan passes in CI with zero secrets detected. All secrets stored in AWS Secrets Manager or GitHub Actions secrets.
**Verification:** Gitleaks CI check passes in GitHub Actions workflow. Code review confirms all secrets referenced via AWS SDK SecretsManager client or GitHub Actions `${{ secrets.* }}` syntax.  
**Exception:** No exceptions.

---

### [ ] [L1] [SEC-3.3-AUDIT] mvn dependency:check (Java) or npm audit (React) produces 0 Critical findings in CI.
**Verification:** Maven or npm CI check passes. Build log shows zero Critical dependency vulnerabilities.  
**Exception:** No exceptions.

## 📚 Documentation

### [ ] [L2] [BUG-FIX-ROOT-CAUSE] Root cause documented in bug ticket with clear explanation of why bug occurred.
**Verification:** Bug ticket (Jira) contains "Root Cause Analysis" section with explanation. PR description references this analysis.  
**Exception:** No exceptions.

---

### [ ] [L3] [TEAM-KAFKA] If bug involved Kafka event processing, event schema documentation updated in docs/events/.
**Verification:** If bug was in Kafka consumer or producer, `docs/events/{topic-name}.md` file updated with corrected event handling logic or schema.  
**Exception:** Not applicable if bug did not involve Kafka event processing.

## ⚙️ CI / Deployment Gate

### [ ] [L1] [CI-ALL-CHECKS] All GitHub Actions CI checks pass (lint, build, unit tests, integration tests, security scans, coverage).
**Verification:** GitHub PR status shows all checks green. No failed or skipped checks.  
**Exception:** No exceptions.

---

### [ ] [L3] [TEAM-POSTGRESQL] If bug involved database queries, PostgreSQL EXPLAIN ANALYZE output attached to PR showing query performance.
**Verification:** If bug was caused by slow or incorrect SQL query, PR description includes EXPLAIN ANALYZE output showing improved query plan.  
**Exception:** Not applicable if bug did not involve database queries.

## ✅ Acceptance & Sign-off

### [ ] [L2] [BUG-FIX-VERIFICATION] Bug reporter or QA Engineer has verified fix in staging environment.
**Verification:** Bug ticket shows comment from original reporter or QA confirming fix verified in staging. Screenshot or test evidence attached.  
**Exception:** EM can approve merge if reporter unavailable and QA Lead confirms verification.

---

### [ ] [L2] [BUG-FIX-PROD-IMPACT] If bug caused production incident, incident ticket (INC-XXX) linked in PR and post-incident review completed.
**Verification:** PR description contains link to incident ticket. Incident ticket shows "Post-Incident Review Complete" status.  
**Exception:** Not applicable if bug did not cause production incident.

## 🔮 Future Candidate Criteria

These criteria are aspirational and not yet enforced. They may be promoted to L3 after team capability assessment and tooling setup:

- **Mutation testing coverage** (PIT) for critical business logic modules (requires team training on mutation testing practices)
- **Chaos engineering experiment** for bug fixes in high-availability services (requires Chaos Monkey or similar tooling setup)
- **A/B testing verification** for bug fixes affecting user-facing features (requires feature flag infrastructure maturity)
