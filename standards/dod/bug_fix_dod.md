## Overview

This Definition of Done applies to all bug fix work items in the Commerce Platform team's backlog. Every criterion must be met before a bug fix PR can be merged to the main branch.

**Legend:**
- **[L1]** = Universal criterion, applies to all work types, no exceptions
- **[L2]** = Work type-specific criterion, applies to all bug fixes
- **[L3]** = Team-specific criterion based on Commerce Platform tech stack
- **[L4]** = Story-specific criterion added during grooming (optional)

**Exception Policy:**
- [L1] criteria cannot be overridden. Any proposed modification requires EM + CISO sign-off.
- [L2] criteria may be exempted for one sprint with EM written justification in PR description.
- [L3] criteria may be exempted with Tech Lead approval, reviewed quarterly.
- [L4] criteria must not contradict L1–L3.

## Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
**Verification:** GitHub PR page shows 2+ approvals with at least 1 from senior engineer or tech lead role.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-SIGN] All commits in PR are signed with GPG or SSH key registered in GitHub.
**Verification:** GitHub commit history shows "Verified" badge on all commits.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-CONV] All commit messages follow Conventional Commits format: type(scope): description.
**Verification:** GitHub Actions conventional-commits-check workflow passes. All commits match pattern: `fix(scope): description`.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-MERGE] PR uses squash merge strategy. No merge commits permitted on main branch.
**Verification:** GitHub PR settings show "Squash and merge" selected. Git log on main shows no merge commits after PR merge.  
**Exception:** No exceptions.

**Verification:** SonarQube dashboard shows Quality Gate status = PASSED. Complexity metric shows 0 methods exceeding 10.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-LOC] No method exceeds 50 lines of code (verified by SonarQube).
**Verification:** SonarQube "Lines of Code per Method" metric shows 0 violations for changed files.  
**Exception:** No exceptions.

**Exception:** No exceptions.

## Test Coverage & Quality

### [ ] [L1] [QA-2.1-COVERAGE] JaCoCo reports ≥80% line coverage on all changed modules in CI build.
**Verification:** GitHub Actions JaCoCo step shows line coverage ≥80% for all changed Java files. JaCoCo HTML report attached to PR.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COVERAGE] JaCoCo reports ≥75% branch coverage on all changed modules in CI build.
**Verification:** GitHub Actions JaCoCo step shows branch coverage ≥75% for all changed Java files. JaCoCo HTML report attached to PR.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COVERAGE] CI build fails if any existing covered code loses coverage (coverage regression check passes).
**Verification:** GitHub Actions coverage-diff workflow shows 0 files with decreased coverage compared to main branch.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-UNIT] Unit tests present for all new/changed production code (JUnit 5 + Mockito).
**Verification:** At least 1 new or modified test file in `src/test/java/` for each changed production file in `src/main/java/`. Tests execute in GitHub Actions.  
**Exception:** EM can grant one-sprint exemption with written justification in PR description.

### [ ] [L2] [QA-2.3-REGRESSION] Regression test covering exact reproduction path from original bug report present in CI. Test fails on pre-fix code and passes post-fix.
**Verification:** New test file named `*RegressionTest.java` or existing test file with `@DisplayName` referencing bug ticket ID. PR description includes: 1) link to test, 2) screenshot/log of test failing before fix, 3) screenshot/log of test passing after fix.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-INTEGRATION] Integration test covering bug reproduction path if bug involved inter-service or database interaction.
**Verification:** Test annotated with `@SpringBootTest` present in `src/test/java/` that exercises the full integration path described in bug report. Test passes in CI.  
**Exception:** EM can grant one-sprint exemption if bug is purely business logic with no integration points.

### [ ] [L2] [QA-2.2-E2E] E2E regression test if bug manifested in UI layer (Playwright).
**Verification:** New or updated Playwright test file in `e2e/tests/` that reproduces the user-visible bug. Test passes in GitHub Actions Playwright workflow.  
**Exception:** EM can grant one-sprint exemption if bug is backend-only with no UI impact.

### [ ] [L2] [From INC-003] Regression test covering exact reproduction path from original bug report present in CI. Test fails on pre-fix code and passes post-fix.
**Verification:** Test file includes comment referencing original bug ticket ID. PR description documents pre-fix failure and post-fix success with CI logs or screenshots.  
**Exception:** No exceptions.  
**Source:** Escaped defect INC-003 (Bug INC-001 reappeared in the next sprint due to missing regression test).

**Verification:** GitHub Actions Snyk workflow shows status = PASSED. Snyk dashboard shows 0 Critical and 0 High issues for this PR.  
**Exception:** No exceptions.

**Verification:** PR description includes "Snyk Medium Findings:" section with Jira ticket IDs for each Medium issue. Jira tickets exist and are assigned.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.2-SECRETS] Gitleaks scan passes in CI with 0 secrets detected.
**Verification:** GitHub Actions Gitleaks workflow shows exit code 0. No secrets, tokens, API keys, or passwords detected in commit history.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.3-DEPS] All third-party dependencies present in approved dependency registry or explicitly approved in PR.
**Verification:** If new dependencies added: PR includes comment from Tech Lead approving dependency, OR dependency matches entry in `docs/approved-dependencies.yaml`.  
**Exception:** No exceptions.

**Verification:** GitHub Actions dependency-check workflow shows 0 Critical CVEs. Maven `dependency-check-report.html` or npm audit output attached to PR shows no Critical vulnerabilities.  
**Exception:** No exceptions.

## Documentation

### [ ] [L2] [BUG-FIX-BEST-PRACTICE] Root cause documented in PR description or linked bug ticket.
**Verification:** PR description includes "Root Cause:" section with technical explanation, OR Jira ticket linked in PR has Root Cause field populated.  
**Exception:** EM can grant exemption if root cause analysis is documented in separate post-mortem document linked in PR.

### [ ] [L3] [COMMERCE-PLATFORM-STANDARD] If bug affected production, runbook updated with troubleshooting entry (docs/runbooks/).
**Verification:** Git diff shows new or updated Markdown file in `docs/runbooks/` with section describing bug symptoms, diagnosis steps, and resolution. File committed in this PR.  
**Exception:** Tech Lead approval if bug was dev/staging-only and never reached production.

### [ ] [L1] [CI-UNIVERSAL-GATE] All GitHub Actions workflows pass: build, test, lint, security (Snyk, Gitleaks), coverage.
**Verification:** GitHub PR checks page shows green checkmarks for all required workflows. No skipped or ignored failures.  
**Exception:** No exceptions.

### [ ] [L3] [COMMERCE-PLATFORM-KAFKA] If bug involves Kafka message handling, integration test with embedded Kafka verifies message processing.
**Verification:** Test annotated with `@EmbeddedKafka` present in `src/test/java/` that sends test message and asserts correct processing. Test passes in CI.  
**Exception:** Tech Lead approval if bug is unrelated to Kafka message processing.

## Acceptance & Sign-off

### [ ] [L2] [BUG-FIX-ACCEPTANCE] Bug reporter or QA engineer verifies fix in staging environment before PR approval.
**Verification:** PR includes comment from original bug reporter or QA engineer confirming successful verification in staging. Comment includes staging URL and verification steps performed.  
**Exception:** EM can grant exemption if original reporter is unavailable and QA Lead provides sign-off.

### [ ] [L3] [COMMERCE-PLATFORM-STANDARD] If bug was P1 or P2 severity, Tech Lead explicitly approves PR.
**Verification:** GitHub PR approvals include Tech Lead approval. PR label "high-priority" or "P1" or "P2" present.  
**Exception:** No exceptions for P1/P2 bugs.
