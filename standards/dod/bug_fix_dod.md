## Overview

This Definition of Done applies to all bug fix work items in the Commerce Platform team backlog. Every criterion must be satisfied before a bug fix PR can be merged to main.

**Legend:**
- **[L1]** — Universal gate, applies to all work types, no exceptions without EM + CISO sign-off
- **[L2]** — Work-type-specific gate, applies to all bug fixes
- **[L3]** — Team-specific gate based on Commerce Platform tech stack
- **[L4]** — Story-specific gate, added during grooming by PO or Tech Lead

## 1. Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
**Verification:** GitHub PR approval count visible in PR page. Verify approver roles in team roster.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2] All commits are signed with GPG or SSH key registered in GitHub.
**Verification:** GitHub displays "Verified" badge on all commits in PR.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-CONV] All commit messages follow Conventional Commits format: type(scope): description.
**Verification:** GitHub Actions workflow "Commit Lint" passes. Manual review of commit history.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-MERGE] PR uses squash merge strategy (not merge commit).
**Verification:** GitHub PR merge button set to "Squash and merge". Repository settings enforce squash merge for main branch.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-COMPLEXITY] SonarQube quality gate passes with cyclomatic complexity ≤10 per method.
**Verification:** SonarQube dashboard shows Quality Gate status "Passed" with 0 complexity violations.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-LOC] No method exceeds 50 lines of code (verified by SonarQube quality gate).
**Verification:** SonarQube dashboard shows 0 "method too long" violations.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-DEAD] SonarQube reports zero dead code issues (unreachable or commented-out code).
**Verification:** SonarQube dashboard shows 0 dead code violations in "Code Smells" category.  
**Exception:** No exceptions.

### [ ] [L2] [BUG-FIX-ROOT-CAUSE] Root cause documented in PR description or linked bug ticket.
**Verification:** PR description contains "Root Cause:" section OR bug ticket (Jira) has root cause field populated.  
**Exception:** EM approval required if root cause unknown. Must include investigation summary.

## 2. Test Coverage & Quality

### [ ] [L1] [QA-2.1-COV] JaCoCo reports ≥80% line coverage on all changed modules.
**Verification:** GitHub Actions "Coverage Report" job passes. JaCoCo XML report shows line coverage ≥80% for changed files.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COV] JaCoCo reports ≥75% branch coverage on all changed modules.
**Verification:** GitHub Actions "Coverage Report" job passes. JaCoCo XML report shows branch coverage ≥75% for changed files.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COV] CI build confirms no existing covered code has lost coverage (coverage non-regression check passes).
**Verification:** GitHub Actions "Coverage Diff" step passes. No lines previously covered are now uncovered.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-UNIT] Unit tests present and passing for all new/changed business logic (JUnit 5).
**Verification:** GitHub Actions "Unit Tests" job passes. Test report shows tests added/updated in src/test/java matching changed production code.  
**Exception:** EM approval if trivial change (e.g., log statement only). Must document justification in PR.

### [ ] [L2] [QA-2.2-INT] Integration tests present and passing if bug was integration-related (service-to-service, database, external API).
**Verification:** GitHub Actions "Integration Tests" job passes. Test report shows integration test covering bug scenario in src/test/java/integration.  
**Exception:** Not required if bug is purely unit-level logic. Tech Lead documents in PR review.

### [ ] [L2] [QA-2.2-E2E] E2E test present and passing if bug was UI-related (React component, user flow).
**Verification:** GitHub Actions "E2E Tests (Playwright)" job passes. Test report shows E2E test covering bug scenario in tests/e2e.  
**Exception:** Not required if bug is backend-only. Tech Lead documents in PR review.

### [ ] [L2] [QA-2.3-REG] [From INC-003] Regression test present covering exact reproduction path from original bug report, failing on pre-fix code and passing on fixed code.
**Verification:** Test file added to appropriate directory (unit/integration/e2e). PR description includes "Regression Test:" section with test file path. Test name clearly references bug ticket ID.  
**Exception:** No exceptions.

## 3. Security

### [ ] [L1] [SEC-3.1-SNYK] Snyk scan reports 0 Critical or High severity findings.
**Verification:** GitHub Actions "Snyk Security Scan" job passes. Snyk dashboard shows 0 Critical/High issues for this PR.  
**Exception:** No exceptions. Findings must be fixed or have CISO-accepted risk waiver documented in PR.

### [ ] [L1] [SEC-3.1-SNYK] All Medium severity findings have tracked Jira tickets created and referenced in PR.
**Verification:** PR description includes "Security Findings:" section with Jira ticket links (format: SEC-NNN). Snyk dashboard shows Medium findings acknowledged.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.2-SECRETS] Gitleaks scan passes with 0 secrets detected in CI.
**Verification:** GitHub Actions "Gitleaks Scan" job passes. No secrets detected in commit history or changed files.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.3-DEP] mvn dependency:check (Java) runs in CI and reports 0 Critical CVE findings.
**Verification:** GitHub Actions "Maven Dependency Check" job passes. OWASP Dependency Check report shows 0 Critical vulnerabilities.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.3-DEP] npm audit (React) runs in CI and reports 0 Critical CVE findings.
**Verification:** GitHub Actions "npm audit" job passes. npm audit report shows 0 Critical vulnerabilities.  
**Exception:** No exceptions.

## 4. Documentation

### [ ] [L1] [L1-UNIVERSAL-DOC] Documentation updated (README, API docs, runbooks) where bug fix impacts user-facing behavior or operations.
**Verification:** git diff shows updates to relevant documentation files (README.md, docs/api/, docs/runbooks/) OR PR description states "Documentation: No changes required" with justification.  
**Exception:** Not required if bug fix is internal logic with no external impact. Tech Lead confirms in PR review.

### [ ] [L2] [BUG-FIX-CHANGELOG] CHANGELOG.md updated with entry under [Unreleased] → Fixed section.
**Verification:** git diff shows CHANGELOG.md entry in "## [Unreleased]" under "### Fixed" with bug ticket reference (format: "- Fixed [BUG-NNN]: description").  
**Exception:** Not required for hotfixes deployed directly to production. Release notes document hotfix separately.

## 5. CI / Deployment Gate

### [ ] [L1] [L1-UNIVERSAL-CI] All CI checks pass: lint, build, unit tests, integration tests, security scans (GitHub Actions).
**Verification:** GitHub PR page shows all required checks with green checkmarks. No failures or warnings.  
**Exception:** No exceptions.

### [ ] [L3] [TEAM-KAFKA-HEALTH] If bug involves Kafka event publishing, integration test verifies event schema matches producer contract.
**Verification:** Integration test in src/test/java/integration/kafka validates event structure against Avro schema. Test passes in CI.  
**Exception:** Not applicable if bug does not touch Kafka event producers. Tech Lead confirms in PR review.

### [ ] [L3] [TEAM-POSTGRESQL-MIGRATION] If bug involves database schema or data migration, Flyway migration script tested in staging environment.
**Verification:** Flyway migration file present in db/migration/. PR description includes "Migration Test:" section with staging test results. DBA approval documented in PR.  
**Exception:** Not applicable if bug does not involve database changes. Tech Lead confirms in PR review.

## 6. Acceptance & Sign-off

### [ ] [L2] [BUG-FIX-REPRO] Bug reporter or QA engineer confirms fix resolves original issue in staging environment.
**Verification:** PR comment from bug reporter or QA engineer stating "Verified in staging. Bug resolved." OR Jira ticket status changed to "Verified".  
**Exception:** EM approval if bug reporter unavailable. QA Lead must verify instead.

### [ ] [L2] [BUG-FIX-NO-SIDE-EFFECTS] QA engineer confirms no new side effects introduced in related features (exploratory testing in staging).
**Verification:** PR comment from QA engineer stating "Exploratory testing complete. No side effects detected." OR test report attached to PR.  
**Exception:** Not required for trivial fixes (e.g., typo, log level). Tech Lead documents justification in PR.
