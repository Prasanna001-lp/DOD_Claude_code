## Overview

This Definition of Done applies to all **Bug Fix** work items in the Commerce Platform team.

Every criterion is:
- **VERIFIABLE** — binary pass/fail with named tool or artifact
- **TRACEABLE** — linked to a source policy or standard
- **SPECIFIC** — names exact tools, commands, or thresholds
- **LAYERED** — tagged L1 (universal), L2 (work type), L3 (team), or L4 (story-specific)

**Criteria Count**: 27 (13 L1-UNIVERSAL, 11 L2-WORKTYPE, 3 L3-TEAM, 1 L4-STORY placeholder)

## 1. Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
**Verification:** GitHub PR page shows 2+ approvals, with at least 1 approval from engineer with "Senior" or "Tech Lead" role in GitHub team membership.  
**Exception:** No exceptions.

### [ ] [L2] [ENG-4.1-SEC] PR touching security-critical code has approval from Security Champion in addition to standard approvals.
**Verification:** GitHub PR shows approval from user tagged as Security Champion if changes touch authentication, authorization, cryptography, or payment processing code.  
**Exception:** EM can grant exemption with written justification if Security Champion unavailable and bug is P0/P1 production incident.

### [ ] [L1] [ENG-4.2] All commits in PR are signed with GPG or SSH key registered in GitHub.
**Verification:** GitHub commit list shows "Verified" badge on every commit in the PR.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2] All commit messages follow Conventional Commits format: type(scope): description.
**Verification:** GitHub Actions workflow "Conventional Commits Check" passes. Format verified: `fix(module): description`.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2] PR merged using squash merge (no merge commits on main).
**Verification:** GitHub PR merge button set to "Squash and merge". Branch protection rule enforces squash merge only.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3] SonarQube quality gate passes with cyclomatic complexity ≤ 10 per method.
**Verification:** SonarQube CI check in GitHub Actions shows "Quality Gate: Passed" with 0 methods exceeding complexity 10.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3] No method exceeds 50 lines of code (SonarQube check).
**Verification:** SonarQube report shows 0 violations of rule "Methods should not have too many lines".  
**Exception:** No exceptions.

### [ ] [L2] [ENG-4.3] No dead code (unreachable, commented-out) present in changed files.
**Verification:** SonarQube report shows 0 "Dead Code" issues in files modified by this PR.  
**Exception:** Tech Lead approval. Reviewed quarterly.

## 2. Test Coverage & Quality

### [ ] [L1] [QA-2.1] JaCoCo reports 80%+ line coverage on all changed modules in CI.
**Verification:** GitHub Actions JaCoCo report shows line coverage ≥ 80% for each module touched by this PR.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1] JaCoCo reports 75%+ branch coverage on all changed modules in CI.
**Verification:** GitHub Actions JaCoCo report shows branch coverage ≥ 75% for each module touched by this PR.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1] No existing covered code has lost coverage (CI fails on coverage regression).
**Verification:** GitHub Actions coverage diff check passes. JaCoCo comparison vs. main branch shows 0% coverage loss on previously covered lines.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-BUG] Unit tests present for bug fix logic (JUnit 5).
**Verification:** JUnit 5 test class exists in `src/test/java` matching package structure of fixed code. Test method names clearly reference bug ticket ID or symptom.  
**Exception:** EM can grant one-sprint exemption with written justification.

### [ ] [L2] [QA-2.2-BUG] Integration tests present if bug involves service integration (JUnit 5 + Mockito).
**Verification:** If bug report indicates cross-service or database interaction: JUnit 5 integration test exists in `src/test/java` with `@SpringBootTest` or equivalent annotation. Test mocks external dependencies using Mockito.  
**Exception:** EM can grant one-sprint exemption with written justification.

### [ ] [L2] [QA-2.2-BUG] E2E test present if bug involves UI behavior (Playwright).
**Verification:** If bug report indicates UI rendering, user interaction, or client-side issue: Playwright test exists in `tests/e2e/` directory. Test reproduces exact user journey from bug report.  
**Exception:** EM can grant one-sprint exemption with written justification.

### [ ] [L2] [QA-2.3 / From INC-003] Regression test covering exact reproduction path from original bug report present in CI (JUnit 5).
**Verification:** JUnit 5 test explicitly named using bug ticket ID (e.g., `testBugJIRA123_regression`). Test includes comment linking to original bug report. CI log shows test execution and pass status.  
**Exception:** EM can grant one-sprint exemption with written justification.  
**📌 FROM ESCAPED DEFECT:** INC-003

### [ ] [L2] [QA-2.3] Regression test documented to fail on pre-fix code and pass on fixed code.
**Verification:** PR description or commit message includes statement "Verified: test fails on commit [SHA] (pre-fix) and passes on commit [SHA] (post-fix)".  
**Exception:** EM can grant one-sprint exemption with written justification.

### [ ] [L3] [TEAM-STANDARD] Bug fix includes test for null/empty input if applicable to bug context.
**Verification:** If bug involves input validation or data handling: JUnit 5 test includes `@ParameterizedTest` or explicit test cases for null, empty string, empty collection.  
**Exception:** Tech Lead approval. Reviewed quarterly.

## 3. Security

### [ ] [L1] [SEC-3.1] Snyk scan shows 0 Critical or High severity findings.
**Verification:** GitHub Actions Snyk check passes. Snyk report accessible via PR comment shows 0 Critical and 0 High vulnerabilities.  
**Exception:** No exceptions. Findings must be fixed or have a CISO-accepted risk waiver before merge.

### [ ] [L1] [SEC-3.1] Snyk Medium severity findings have tracked Jira tickets before merge.
**Verification:** If Snyk report shows Medium findings: PR description includes Jira ticket IDs for each Medium finding (format: JIRA-1234). Jira tickets exist and are in Open or In Progress status.  
**Exception:** No exceptions.

### [ ] [L1] [SEC-3.2 / SEC-4.2] Gitleaks scan passes with 0 secrets detected in CI.
**Verification:** GitHub Actions Gitleaks check passes. No "Secret detected" alerts in CI log.  
**Exception:** No exceptions. All secrets must be removed or rotated before merge.

### [ ] [L1] [SEC-3.3] npm audit (Node.js) or mvn dependency:check (Java) reports 0 Critical CVE findings in CI.
**Verification:** GitHub Actions dependency check passes. For Java modules: `mvn dependency-check-maven` plugin shows 0 Critical CVEs. For Node.js modules: `npm audit --production --audit-level=critical` exits with code 0.  
**Exception:** No exceptions.

## 4. Documentation

### [ ] [L2] [TEAM-STANDARD] Root cause documented in PR description or linked bug ticket.
**Verification:** PR description includes "Root Cause:" section with technical explanation. OR: Jira ticket linked in PR has Root Cause field populated.  
**Exception:** EM can grant one-sprint exemption with written justification.

### [ ] [L2] [TEAM-STANDARD] CHANGELOG.md updated with bug fix entry under [Unreleased] section.
**Verification:** `git diff` shows `CHANGELOG.md` modified. New entry exists under `[Unreleased]` section in format: "### Fixed - [JIRA-ID] Brief description of bug fix".  
**Exception:** EM can grant one-sprint exemption with written justification.

### [ ] [L3] [TEAM-STANDARD] Inline code comments added if fix involves non-obvious logic or workaround.
**Verification:** If fix includes defensive programming, edge case handling, or workaround: `git diff` shows comments explaining why (not just what) the code does.  
**Exception:** Tech Lead approval. Reviewed quarterly.

## 5. CI / Deployment Gate

### [ ] [L1] [TEAM-STANDARD] All GitHub Actions CI checks pass (lint, build, test, security scan).
**Verification:** GitHub PR page shows green checkmarks for all required status checks. No failed or pending checks.  
**Exception:** No exceptions.

### [ ] [L2] [TEAM-STANDARD] Bug fix verified in staging environment before merge.
**Verification:** PR description includes "Staging Verification:" section with timestamp, tester name, and confirmation that bug no longer reproduces in staging deployment.  
**Exception:** EM can grant one-sprint exemption with written justification.

## 6. Acceptance & Sign-off

**Exception:** EM can grant one-sprint exemption with written justification.

**Exception:** Tech Lead approval. Reviewed quarterly.
