## Purpose

This Definition of Done checklist ensures every **release** item meets Acme Engineering's quality, security, and operational standards before production deployment. All criteria marked **[L1]** and **[L2]** are mandatory. **[L3]** criteria are team-specific for Commerce Platform. **[L4]** criteria are added during release planning by the Product Owner or Tech Lead.

---

## How to Use This Checklist

1. **During Release Planning**: Review this checklist with EM, PO, and Tech Lead. Add any [L4] story-specific criteria.
2. **Before Creating Release PR**: Verify all [L1] and [L2] criteria can be met. Flag blockers immediately.
3. **During Release Testing**: Complete TEST-01, TEST-02, DEPLOY-01 in staging/pre-prod environments.
4. **Before Production Deployment**: EM and PO sign-off (ACCEPT-01, ACCEPT-02) required.
5. **Post-Deployment**: Complete TEST-03 (smoke tests in production) before closing release ticket.

**If any [L1] or [L2] criterion fails**: release is BLOCKED. Escalate to EM.

## Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
- **Verification**: GitHub PR page shows 2+ approvals. At least 1 approver has "Senior Engineer" or "Tech Lead" role in GitHub team settings.
- **Exception**: No exceptions.

### [ ] [L1] [ENG-4.2-SIGN] All commits in PR are signed with GPG or SSH key registered in GitHub.
- **Verification**: GitHub displays "Verified" badge on all commits in the PR.
- **Exception**: No exceptions.

### [ ] [L1] [ENG-4.2-CONV] All commit messages follow Conventional Commits format: type(scope): description.
- **Verification**: commitlint GitHub Action check passes. All commits match pattern: `(feat|fix|docs|chore|refactor|test|ci)(scope): message`.
- **Exception**: No exceptions.

### [ ] [L1] [ENG-4.3-COMPLEXITY/LOC/DEAD] SonarQube quality gate passes: cyclomatic complexity ≤10 per method, no methods >50 lines of code, 0 dead code issues.
- **Verification**: SonarQube status check shows "Passed" in GitHub PR checks. SonarQube dashboard shows 0 issues for complexity, code smells (dead code), and method length.
- **Exception**: No exceptions.

## Security

### [ ] [L1] [SEC-3.1-SNYK] Snyk scan reports 0 Critical or High severity findings.
- **Verification**: Snyk GitHub Actions check passes. Snyk dashboard shows 0 Critical and 0 High vulnerabilities for this release branch.
- **Exception**: No exceptions. Critical/High findings must be fixed or have CISO-accepted risk waiver documented in Jira.

### [ ] [L1] [SEC-3.1-SNYK] All Medium severity findings from Snyk have corresponding Jira tickets linked in PR.
- **Verification**: Snyk report lists Medium findings. Each has a Jira ticket link in PR description or comments (format: `JIRA-NNNN`).
- **Exception**: No exceptions. Medium findings without tickets block merge.

### [ ] [L1] [SEC-3.2-SECRETS] Gitleaks scan passes in CI with 0 secrets detected.
- **Verification**: Gitleaks GitHub Actions check shows "passed" status. No leaked secrets reported in workflow logs.
- **Exception**: No exceptions.

### [ ] [L1] [SEC-3.3-DEPS] mvn dependency:check reports 0 Critical CVE findings in CI.
- **Verification**: Maven dependency check GitHub Action passes. Build log shows "No vulnerable dependencies found with CRITICAL severity".
- **Exception**: No exceptions. Critical CVEs must be patched before release.

### [ ] [L1] [SEC-4.2-SECRETS-MGMT] All secrets stored in AWS Secrets Manager or GitHub Actions secrets. Verified by Gitleaks scan passing.
- **Verification**: Gitleaks passes (see SEC-03). Manual review confirms no hardcoded credentials in `application.properties`, config files, or Terraform variables.
- **Exception**: No exceptions.

## Deployment & Rollback Readiness

### [ ] [L2] [QA-3.1-RELEASE] Rollback plan documented in runbook and tested successfully in staging.
- **Verification**: Confluence runbook page includes "Rollback Procedure for vX.Y.Z" section. GitHub Actions workflow "Test Rollback - Staging" shows successful execution within last 24 hours.
- **Exception**: No exceptions. Untested rollback plans block production release.

### [ ] [L3] [TEAM-KAFKA-COMPAT] Kafka message schema changes are backward-compatible or have coordinated deployment plan with downstream consumers.
- **Verification**: If Kafka schema changed: Schema Registry shows new version is compatible (Confluent Schema Registry compatibility check passes). OR: Jira ticket exists documenting coordinated deployment plan with downstream teams.
- **Exception**: Not applicable if no Kafka schema changes. Document "N/A - no Kafka changes" in PR description.

### [ ] [L3] [TEAM-DB-MIGRATION] Database migration scripts tested in staging and pre-prod. Rollback SQL scripts verified.
- **Verification**: If database schema changes: Flyway/Liquibase migration logs in staging and pre-prod show successful migration. Rollback scripts exist in `db/rollback/` directory and tested in staging (documented in PR comments).
- **Exception**: Not applicable if no database changes. Document "N/A - no DB changes" in PR description.
