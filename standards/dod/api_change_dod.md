## Overview

This Definition of Done applies to all work items classified as **API Change** for the Commerce Platform team. An API Change includes:

- Adding, modifying, or removing REST API endpoints
- Changing request/response schemas or status codes
- Modifying API contracts consumed by external teams or services
- Updating OpenAPI specifications

All criteria must be verified before the pull request is merged to main. Criteria are layered as follows:

- **[L1-UNIVERSAL]** — Applies to ALL work items, no exceptions
- **[L2-WORKTYPE]** — Applies to all API Change items
- **[L3-TEAM]** — Commerce Platform team-specific standards
- **[L4-STORY]** — Story-specific additions defined during grooming

## Code Quality

### [ ] [L1] [ENG-4.1] PR has minimum 2 approvals from engineers other than the author, including 1 from a senior engineer or tech lead.
**Verification:** GitHub PR approval count visible in PR UI. Verify at least 1 approval is from engineer with "Senior" or "Tech Lead" title in GitHub team membership.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-SIGN] All commits in PR are signed with GPG or SSH key registered in GitHub.
**Verification:** GitHub UI displays "Verified" badge on all commits in PR commit history.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-CONV] All commit messages follow Conventional Commits format: type(scope): description.
**Verification:** GitHub Actions workflow "commitlint" check passes. Manual verification: each commit message starts with type(scope): pattern.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.2-MERGE] PR uses squash merge strategy. No merge commits permitted on main branch.
**Verification:** GitHub PR merge button set to "Squash and merge". Branch protection rules enforce squash merge only.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-COMPLEX] SonarQube quality gate passes with cyclomatic complexity ≤10 per method.
**Verification:** SonarQube dashboard shows Quality Gate status "Passed". Complexity metric displays no methods exceeding threshold of 10.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-LOC] No method exceeds 50 lines of code (verified by SonarQube).
**Verification:** SonarQube code smells section reports 0 methods exceeding 50 lines of code.  
**Exception:** No exceptions.

### [ ] [L1] [ENG-4.3-DEAD] No dead code present: SonarQube reports 0 unreachable code blocks and 0 commented-out code sections.
**Verification:** SonarQube issues tab filtered by type "Dead Code" shows 0 issues. Code Smells section shows no commented-out code warnings.  
**Exception:** No exceptions.

### [ ] [L3] [ENG-4.1-SEC] PRs touching security-critical code paths include approval from designated Security Champion.
**Verification:** GitHub PR approvals include username matching Security Champion roster (defined in team README.md). If no security-critical paths touched, N/A.  
**Exception:** Tech Lead approval. Exemption requires written justification in PR description explaining why Security Champion review was not feasible within sprint timeline.

## Test Coverage & Quality

### [ ] [L1] [QA-2.1-COVERAGE] JaCoCo reports ≥80% line coverage on all changed modules in CI build.
**Verification:** GitHub Actions job "Test Coverage" passes. JaCoCo report in build artifacts shows line coverage percentage ≥80% for each changed Java package.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COVERAGE] JaCoCo reports ≥75% branch coverage on all changed modules in CI build.
**Verification:** JaCoCo report in GitHub Actions build artifacts shows branch coverage percentage ≥75% for each changed Java package.  
**Exception:** No exceptions.

### [ ] [L1] [QA-2.1-COVERAGE] CI build fails if any existing covered code loses coverage (coverage regression check passes).
**Verification:** GitHub Actions job "Coverage Regression Check" passes. Job compares coverage delta between base branch and PR branch, fails if any file shows negative delta.  
**Exception:** No exceptions.

### [ ] [L2] [QA-2.2-UNIT] Unit tests present for all new/changed production code (JUnit 5 + Mockito).
**Verification:** PR diff shows corresponding *Test.java file(s) in src/test/java/ for each changed production class. Unit tests execute in GitHub Actions "Unit Tests" job.  
**Exception:** EM approval. Exemption permitted for one sprint if story is pure configuration change with no business logic (must be documented in PR description).

### [ ] [L2] [QA-2.2-INTEGRATION] Integration tests present and passing in CI for all new/changed integration points.
**Verification:** PR diff shows *IntegrationTest.java file(s) in src/test/java/ covering changed API endpoints or service integrations. GitHub Actions job "Integration Tests" passes.  
**Exception:** EM approval. Exemption permitted for one sprint if API change is purely additive (new optional field) with no behavioral change. Exemption must be documented in PR description.

### [ ] [L2] [From INC-002] API contract test includes test cases for all nullable fields documented in OpenAPI specification.
**Verification:** Contract test class (e.g., *ContractTest.java) includes explicit test methods for each nullable field in the changed API endpoint. Test verifies null value handling. OpenAPI spec file (api/openapi.yaml) lists fields as nullable: true.  
**Exception:** No exceptions. This criterion was added due to escaped defect INC-002.

### [ ] [L3] [QA-2.4-PERF] k6 load test present in CI for user-facing API endpoints expected to handle >1000 RPS.
**Verification:** If endpoint serves >1000 RPS traffic (documented in API performance baseline spreadsheet), k6 test script exists in tests/load/ directory. GitHub Actions job "Load Tests" executes k6 script.  
**Exception:** Tech Lead approval. Exemption permitted if endpoint is internal-only or expected traffic is <1000 RPS. Document exemption reason in PR description.
